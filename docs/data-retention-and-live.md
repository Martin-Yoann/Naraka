# 独立抽签刷新与数据保留

## 两条数据路径

常规行情继续由 GitHub Actions 每小时第7、37分钟计划采集。单轮限制220次上游请求、100次详情核验、6分钟运行时间，并按官方类型保存分页断点。

抽签页的“实时刷新抽签”通过 `POST /api/lottery/refresh` 单独执行，不等待常规轮次。可使用页面下方的谪星筛选指定类型；未指定时查询全站最新上架商品中的谪星。请求会读取最新上架前2页（最多30条列表），并补充数据库已有候选，最多核验12件真实详情。上游查询间隔至少1.6秒，单次请求超时最多8秒，整轮抓取预算45秒。列表未包含的商品、超过核验上限的候选均可能遗漏，页面不宣称覆盖全市场。

全站共用60秒刷新冷却和数据库租约，同时访问者共享本轮结果；冷却期间返回202及已有结果、执行状态与查询范围。刷新是按需采样，不是实时推送。页面自动轮询只读取已经保存的数据，不触发上游抓取。上游异常时停止继续请求，保留此前观察并显示错误，不将异常视为商品成交或没有抽签。

## 存储与写入

- 普通行情批次在 `zx_batches`。
- 独立抽签快照在 `zx_settings` 的 `lottery-live.json`，最多120件有效且近期确认的商品，覆盖写入而不追加普通行情批次。
- 执行状态在 `lottery-refresh.json`。
- 同款＋已解锁孔数的历史最低价在 `lottery.json`。首次建立基线，严格低于已有记录才记事件；最近最多保留1000条新低事件。
- 最多12件核验结果批量写入库存与观察；以实际观察时间防止较旧结果覆盖较新数据。
- 列表查询在 PostgreSQL 侧去掉大体积预览帧；完整预览通过单件接口读取。行情函数实例内有10秒合并读取缓存，更新后本实例立即失效，其他实例最长可能延迟10秒。

## 每3天清理一次

用户选择的规则为：每满72小时执行一次周期清理，在执行时删除早于72小时前的明细。每轮 Actions 完成后检查到期状态，因此实际执行可能受任务调度延迟影响。两次清理之间，明细可自然增长到接近6天；这与每天保持3天滑动窗口不同。

另外，每轮采集后的维护都会检查以下总量上限，超限时优先淘汰最旧记录，不必等到下次周期清理：

| 内容 | 上限 |
| --- | ---: |
| 保留的不同商品 | 20,000件 |
| 逐件观察记录 | 200,000条 |
| 普通行情批次 | 300批 |
| 独立抽签当前快照 | 120件 |
| 已记录的新低事件 | 最近1,000条 |

史低汇总不按三天删除；史低、最近观察、当前样本对应的少量库存记录被保护，包含在商品总量上限中，以保留核验流水号与外观预览。静态图鉴资源、官方类型目录和断点也不清理。无引用的媒体记录在清理时移除。

趋势只能展示实际保留的原始采样；选择7天、30天不会恢复已删除明细，页面已提示可能不完整。

## 检查与操作

`GET /api/storage` 返回统计时间、行数、业务表物理大小、最近和下一次到期清理时间。业务表大小含索引与可复用页面，不等于项目的全部计费用量，也不会在删除后立刻等比例下降。

```sh
npm run db:migrate
npm run db:maintain -- --dry-run
npm run db:maintain
```

`--dry-run` 只计算周期清理候选，不执行删除。真实维护在事务中进行，失败回滚；脚本使用租约避免同类维护重叠。不要手动清空 `lottery.json`，否则史低基线会丢失。

运行 `npm test` 检查清理周期、行数上限、史低及预览保护、刷新限额、并发冷却、上游失败和较旧结果晚到场景。连接真实 Neon 的 Next.js 服务启动后，`node scripts/live-lottery-qa.mjs` 可验证真实抓取与浏览器交互；该检查会实际消耗一轮共享刷新。

## 免费额度

本次实测业务表约22 MB，容量适合先试用。容量控制无法保证计算或传输额度永远够用：持续打开网页会保持查询，访问者增加也会增加函数和数据库消耗。请同时查看 Neon 项目的实际计算、传输和存储用量，额度以控制台及官方当前套餐说明为准。
